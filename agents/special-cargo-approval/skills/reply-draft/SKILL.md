# 회신 초안

> 에이전트: 스페셜화물 승인 보조 에이전트 (kim jaehyung) · 상태: **작성됨** · 코드: `dashboard/js/approval/drafts.js` · 화면: `dashboard/js/approval/board.js` 의 점검표 시트

## 언제 쓰나
`doc-check` 가 요청 1건을 판정한 뒤. 담당자가 카드를 눌러 점검표를 확인하고, 초안을 고쳐 복사한다. 발송은 담당자가 원 메일에 직접 회신해서 한다.

## 입력
`doc-check` 의 요청별 결과(`draft` 종류 · 확인 사항의 영문 문장 · 판정된 화물). 이름은 가린 상태(선박 S01 · 컨테이너 C01 · 발신처 L01).

## 하는 일 (순서대로)
1. `draft` 가 `none` 이면 **초안을 만들지 않는다**. 화면에는 「직접 확인이 필요해 초안을 만들지 않았습니다」와 확인할 단계를 보여 준다.
2. `approve`(가능): 승인 초안. DG 는 이병선 DG 승인 데스크의 승인안 문구(IMO 규정 준수 · 슬롯 조건 · 추가 비용은 박스 오퍼레이터 부담)를 그대로 쓰고, OOG · Flexibag 는 같은 취지의 문구로 한다(신청 서류와 실제 화물이 다르면 승인 취소).
3. `reject`(불가): 거절 초안. `- Reject Remark -` 아래에 규정 위반 근거(영문)만 번호를 붙여 적는다(예: `UN 1089 is listed in our Prohibited DG List (VER.10 (FOR PARTNERS))`).
4. `supplement`(서류 누락·불일치만): 보완 요청 초안. 빠진 서류와 서로 다른 값을 적고 다시 보내 달라고 한다. 승인도 거절도 아니라서 화면에서 「// 보류, 사용자 추가 확인 요함//」 표시를 붙이고, 복사할 때 맨 위에 자동으로 붙인다(보낼 때 지운다).
5. 부킹번호 · 선박명 · 담당자 서명 · 전화번호 · 이메일은 `[대괄호]` 자리표시로 남긴다. 사람이 원 메일을 보고 채운다.

## 출력
- 화면 글 초안(복사 버튼만, 보내기·Outlook 저장 없음). 결과 파일에는 초안 본문을 넣지 않는다(건수·판정만).
- 초안 종류별 건수는 `data/out/special-cargo-docs.json` 의 `table` 판정 칸과 `metrics` 로 이미 나온다.

## 확인 필요로 넘길 때
- 점검 결과가 직접 확인(IMDG 다름 · 못 읽음 · 농도 다름 · 자료 없음)이면 초안을 만들지 않는다 — 맞다고 처리해 승인 문구를 쓰지 않는다.
- 규정 위반과 직접 확인이 겹치면 거절 초안에는 규정 위반 근거만 적는다. 직접 확인 사항은 초안에 넣지 않고 점검표 ③ 규정 단계에 「확인」으로 남으니, 보내기 전에 담당자가 같이 본다.
- 거절 사유가 서류 누락·불일치뿐인 건을 거절 초안으로 쓰지 않는다 — 보완 요청 초안을 쓴다.
